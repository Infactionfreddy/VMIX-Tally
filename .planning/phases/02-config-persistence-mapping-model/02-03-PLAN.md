Recovery behaviors to add inside init() (per D-11, D-12, RESEARCH Pattern 1):

1. Missing file: db.read() returns null on ENOENT — db.data stays DEFAULTS. After read,
   call db.write() to materialise a fresh config.json. No catch needed for this path.

2. Corrupt JSON: db.read() throws SyntaxError — catch it, call
   rename(this.path, this.path + ".bak-corrupt") from node:fs/promises (swallow its
   own error with .catch(()=>{})), call this.logger("[config] CORRUPT …"), then reset
   db.data = structuredClone(DEFAULTS) and await db.write() to create a fresh file.

3. Schema-invalid-but-valid-JSON (RESEARCH Pitfall 3): After a successful db.read(),
   run schema.safeParse(db.data). If !parsed.success, execute the SAME quarantine path
   as (2): rename → .bak-corrupt, loud log, reset to DEFAULTS, write fresh file.

Logger injection pattern (RESEARCH §Supporting libs A4):
  constructor(path?: string, logger?: (msg: string) => void)
  Default: (msg) => console.error(msg)
  Tests inject a spy to assert "loud log" without real stderr.

node:fs/promises import (RESEARCH §Supporting libs):
  import { rename } from "node:fs/promises";
  The bak path is always: this.path + ".bak-corrupt"
  (sibling to config.json, never from external input — no path traversal)

From src/config/schema.ts (Plan 02-01):
  schema.safeParse(unknown) → { success: true, data: PersistedConfig } | { success: false, error: ZodError }

lowdb v7 call shapes verified in 02-02:

  db.data = structuredClone(DEFAULTS); await db.write()  // reset + persist

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| on-disk config.json → ConfigStore.init() | File content is untrusted (hand-edited, partially written, garbage bytes). Crosses into in-memory state only after safeParse passes. |
| ConfigStore.init() → node:fs/promises rename | Bak path derived as `configPath + ".bak-corrupt"` from a code-controlled value, not from the file contents. |
| ConfigStore logger → process stderr | Log message includes the config path and error string. Both are operator-controlled strings on a local single-user tool. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-08 | Denial of Service | Corrupt or schema-invalid config.json crashes the server process on boot | mitigate | D-11/D-12 total-function boot: catch SyntaxError from db.read(); run safeParse after successful read; both paths quarantine + reset to DEFAULTS + write fresh file — process never crashes (ASVS V5) |
| T-02-09 | Tampering | Silent overwrite of corrupt config destroys operator's recovery data | mitigate | Quarantine-not-overwrite: rename to `.bak-corrupt` BEFORE writing defaults, preserving the bad file for manual inspection (D-12 requirement) |
| T-02-10 | Tampering | Path traversal via bak-corrupt path derived from config path | accept | Bak path is always `configPath + ".bak-corrupt"` — a constant suffix appended to the constructor-injected (code-controlled) config path, never derived from file contents or external runtime input; LAN single-operator tool (ASVS V12) |
| T-02-11 | Information Disclosure | Loud log exposes config path in stderr | accept | Config path is a local filesystem path on an operator-controlled machine; no secrets in the log message; `console.error` writes to local process stderr only; injectable logger keeps tests clean |
| T-02-12 | Availability | rename() to .bak-corrupt fails (e.g. permissions, AV lock on Windows) | mitigate | `.catch(()=>{})` swallows rename errors — boot continues on defaults regardless; operator may not recover the bak file, but the process never hangs or crashes (availability over recovery) |
| T-02-SC | Tampering | npm installs (lowdb, zod, steno, node:fs) | accept | lowdb/zod/steno slopcheck-clean (02-01 Plan T-02-SC); node:fs is a Node.js built-in — no install, no postinstall, no supply-chain surface |
</threat_model>
